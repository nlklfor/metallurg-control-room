# Metallurg Control Room — Audit (September 2026)

First full walkthrough of the repo + live Supabase (`metallurgStore`, `ytynsqcxteyufoynvsir`).

## Verdict on the "browser writes with anon key" concern

**Not a hole — the database enforces access properly.** RLS is enabled on every
`public` table, and the policies are keyed off a real admin model, not the app:

| Table       | RLS | Policies |
|-------------|-----|----------|
| `products`  | on  | `public` SELECT; `authenticated` INSERT/UPDATE/DELETE gated by `is_admin()` |
| `orders`    | on  | `authenticated` SELECT/UPDATE/DELETE gated by `is_admin()`; no INSERT policy (bot writes via service role) |
| `bot_users` | on  | `authenticated` SELECT gated by `is_admin()`; no write policy |
| `reviews`   | on  | `public` SELECT; `public` INSERT gated by `is_order_completed(order_id)` |
| `admins`    | on  | **no policies** → locked to service role only (safe) |
| `lookup_attempts` | on | no policies → locked to service role only (safe) |

```sql
create function public.is_admin() returns boolean
  language sql stable security definer set search_path to 'public'
as $$ select exists (select 1 from public.admins where user_id = auth.uid()); $$;
```

`public.admins` currently holds two users:

- `mtllrg@proton.me` — the store operator (active).
- `nik.slepcov1771@gmail.com` — dev account (signed in once, March 2026).

### Implication for the app gate

The app's `ADMIN_EMAIL` env check and the DB's `admins` table are **two separate
allow-lists that can drift**. If they disagree:

- email matches `ADMIN_EMAIL` but uid not in `admins` → UI loads, every query
  returns empty / silently fails.
- uid in `admins` but email ≠ `ADMIN_EMAIL` → locked out of the UI despite having
  DB access.
